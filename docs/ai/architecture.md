# Architecture — Interview tool

> Статус: **пропозиція, вимагає підтвердження**. Усе нижче — план, а не факт коду.
> Позначки `⚠️ рішення` = відкриті питання, які приймає людина, а не AI.

## Стиль

Шаровий монолит: один Python-процес + одна сторінка респондента.
Провайдери (LLM / STT / TTS) — за адаптерами. Без мікросервісів: інструмент
обслуговує десятки інтервʼю, не десятки тисяч.

## Шари й відповідальність

| Шар | Відповідає за | Не має права |
|---|---|---|
| `web/` (клієнт респондента) | мікрофон, відтворення аудіо, екран згоди, індикація стану, fallback у текст | знати назву вендора; тримати ключі; вирішувати, яке питання наступне |
| `api/` (HTTP-шар) | приймання запитів, валідація, сесійні токени | містити логіку інтервʼю; звертатися до вендорів напряму |
| `interview/` (ядро) | стан інтервʼю, гайд, вибір наступного питання, правила зупинки | знати про HTTP; знати конкретного вендора |
| `providers/llm`, `providers/stt`, `providers/tts` | єдиний інтерфейс до вендора, ретраї, таймаути | містити логіку інтервʼю; знати про БД |
| `analysis/` | транскрипт → структурований звіт (теми, цитати, болі) | правити транскрипт; впливати на живе інтервʼю |
| `storage/` | Supabase: гайди, сесії, реплики, звіти, аудит | містити бізнес-правила |
| `config/` (простір дослідження) | **уся доменна специфіка**: персона інтервʼюера, мови, словник домену для STT, правила приватності, брендинг, схема звіту, вендор і ключі | містити код; знати про інші простори |
| `admin/` (клієнт дослідника) | конструктор гайда, список інтервʼю, звіти | обходити `api/`; існувати в публічному запуску (вмикається прапорцем `--admin`) |

## Правила взаємодії

- Виклики вендорів — **тільки** через `providers/*`. Пряме `requests.post` до
  вендора з будь-якого іншого місця = дефект.
- `interview/` не знає, чи канал голосовий чи текстовий: на вхід — текст реплики,
  на вихід — текст питання. Голос — це `providers/stt` + `providers/tts` навколо.
  **Саме це дає безкоштовний текстовий fallback і робить голос замінним.**
- **Жодних доменних припущень у коді.** Ні «ЄРБ», ні «юрист», ні «LIGA360», ні
  української мови за замовчуванням — усе це значення конфігу простору. Тест на
  дефект: чи можна цим тулом провести інтервʼю про вибір велосипеда, не торкаючись
  жодного `.py`-файла? Якщо ні — доменна деталь протекла в код.
- Ключі й секрети — тільки з env / локального конфігу, ніколи в клієнті й ніколи
  в репозиторії. **Кожен простір має власні ключі й власний білінг.**
- Помилки вендора: ретрай із бекофом → якщо не вийшло, деградація (голос → текст),
  а не обрив інтервʼю. Респондент, який дійшов до 12-ї хвилини, не має втратити все.

## Структура тек (пропозиція)

```
interview-tool/
├── app/
│   ├── api/            # HTTP-роути
│   ├── interview/      # ядро: стан, гайд, правила діалогу
│   │   └── prompts/    # системний промпт інтервʼюера (версіонується!)
│   ├── providers/      # llm/ stt/ tts/ — по файлу на вендора + base.py
│   ├── analysis/       # транскрипт → звіт
│   ├── config/         # схема конфігу простору + валідація
│   └── storage/        # Supabase
├── spaces/             # конфіги просторів (НЕ в git, або в git без ключів)
│   ├── liga-ux/        # корпоративний: словник домену, приватність, брендинг
│   └── example/        # референсний приклад для нового простору
├── web/                # сторінка респондента (згода → інтервʼю → дякуємо)
├── admin/              # конструктор гайда + список інтервʼю + звіти
├── docs/ai/            # контекстні документи (цей каркас)
└── tests/
```

## Потоки даних

### Голосова реплика (один хід)

```
мікрофон → аудіо-чанк → api/ → providers/stt → текст реплики
                                                    ↓
                          storage/ ← реплика ← interview/ (наступне питання)
                                                    ↓
        браузер ← аудіо ← providers/tts ← текст питання
```

⚠️ **рішення:** покроково (записав відповідь → пауза 3–6 с → чуєш питання) чи
дуплексний стрім у реальному часі (можна перебивати).
**Рекомендація: покроково для MVP** — дуплекс у рази складніший і дорожчий, а на
етапі, коли ми ще не знаємо, чи працює сама ідея, це не той ризик, який варто брати.
Пауза лікується індикатором «записую…» / «думаю…».

### Аналіз (після інтервʼю, не в реальному часі)

```
транскрипти сесій → analysis/ (structured output: теми, цитати, болі, суперечності)
                  → звіт по дослідженню + окремий прохід «перевірка на упередженість»
```

Аналіз **асинхронний**: він не має права підвішувати живе інтервʼю.

## Модель даних (пропозиція, ⚠️ вимагає підтвердження)

| Таблиця | Призначення | Ключові поля |
|---|---|---|
| `studies` | дослідження (хвиля) | **space** (простір), назва, мета, статус, дати |
| `guides` | гайд інтервʼю, версіонований | study_id, версія, мета, теми, обовʼязкові питання, ліміти |
| `sessions` | одне інтервʼю | guide_id, статус, згода, канал, тривалість, токен доступу |
| `turns` | реплики по черзі | session_id, роль, текст, аудіо-посилання (опц.), таймінг |
| `reports` | звіт | study_id / session_id, структурований JSON + версія промпту аналізу |
| `audit` | хто дивився транскрипти | навіщо: транскрипти можуть містити чутливе |

⚠️ **рішення:** зберігаємо аудіо чи **тільки транскрипт**?
**Рекомендація: тільки транскрипт у MVP** (аудіо видаляємо одразу після
розпізнавання). Менше персональних даних — простіша згода, простіше зберігання,
менша поверхня ризику. Якщо аудіо потрібне для перевірки якості STT — зберігати
обмежений строк і сказати про це в згоді.

## Версіонування промптів — обовʼязкове

Системний промпт інтервʼюера і промпт аналізу **версіонуються в git, а результати
посилаються на версію**. Без цього неможливо відповісти на питання «а чому в
березневій хвилі інсайти інші — люди змінилися чи ми промпт покрутили?». Це не
формальність: це різниця між дослідженням і генератором тексту.

## Запреты

- **Ніколи** не викликати вендора напряму поза `providers/*`.
- **Ніколи** не логувати вміст реплик разом з ідентифікацією респондента в один
  лог. Транскрипт — у сховище з аудитом, технічний лог — без вмісту.
- **Ніколи** не тягнути дані з продуктових БД LIGA360 у цей інструмент «щоб
  збагатити профіль респондента». Агрегація персональних даних між системами —
  окреме рішення з юридичним департаментом, не побічний ефект тулу.
- **Ніколи** не давати інтервʼюеру доступ до жодного інструменту, крім розмови.
  Він ставить питання й слухає. Усе інше — поверхня для зловживань.
- **Ніколи** не хардкодити доменну лексику, мову, брендинг або схему звіту —
  тільки конфіг простору. Одна протікла деталь робить тул «інструментом для
  LIGA360», і назад його вже ніхто не розкрутить.
- **Ніколи** не приймати текст для озвучення з запиту клієнта. Озвучується лише
  те, що інтервʼюер уже сказав у цій сесії. Інакше ендпоінт — безкоштовний
  TTS-проксі за чужий рахунок.
- **Ніколи** не переносити ім'я голосу між провайдерами: `say`, браузер і Azure
  називають голоси по-різному. Ім'я належить адаптеру, і адаптер його перевіряє.
- **Ніколи** не писати конфіг на диск без валідації тим самим завантажувачем,
  що й реальне інтервʼю. Зламаний гайд мусить завалити форму, а не наступну розмову.
- **Ніколи** не змінювати транскрипт автоматично (окрім явного, залогованого кроку
  деідентифікації). Транскрипт — первинні дані дослідження.
